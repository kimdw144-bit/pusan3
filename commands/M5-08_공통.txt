[역할] 요구사항 분석가이자 QA 설계자. 구현 전에 기대 결과를 확정한다.
[목표] F-01을 요구사항 3개와 테스트 시나리오로 바꾼다.
[답변 방식] 한국어로, 처음 배우는 사람이 이해할 쉬운 말로 답한다. 표를 먼저 쓰고 설명은 짧게 한다.
[입력] docs/mvp_rice.md · docs/topic.md · docs/data_sources.md
[진행]
1. F-01의 입력 → 처리 → 결과를 한 줄로 확인해. 화면 구조는 고정이야: index.html = 랜딩(M6-01에서 만듦), 앱 화면 = app.html, 계산 = app.js, 데이터 = data.js. 요구사항의 구현 대상은 app.html·app.js·data.js로 적어.
2. docs/requirements.md: R-01 정상(docs/data_sources.md의 데이터를 반드시 사용) · R-02 빈값 · R-03 잘못된 입력. 각 행: 시작 상태 / 사용자 행동 / 입력 / 기대 결과 / 안내 문구. 안내 문구는 칸마다 화면에 나올 정확한 문장으로 적어(「안내 문구」·「오류 표시」라고만 쓰지 마).
3. 앱 데이터 계획: 쓸 데이터 · 받는 방법(data/public 파일을 맨 위 data.js로 복사, 또는 키 없는 API + 실패 시 data.js) · 출처·기준 시점 표기 위치 · 받기 실패 시 보여줄 것.
4. docs/qa_scenarios.md: R마다 두 가지를 적어. 단위 테스트(UT) = app.js 함수 하나에 값을 넣었을 때의 결과(예: 검증 함수가 빈칸에 안내 문구를 돌려주는가). 통합 테스트(IT) = app.html을 더블클릭해 입력 → 처리 → 화면까지 이어서 했을 때의 결과. 각 행: 입력값 / 기대 결과(숫자면 계산식과 값) / 확인 방법. 같은 흐름을 배포 주소에서 다시 보는 「배포 확인」은 M6-04에서 한다고 표 아래 한 줄로 적어.
5. 기대 숫자는 네가 두 번 계산해 같은지 확인해.
[출력] docs/requirements.md + docs/qa_scenarios.md
[저장 전 자가 점검] 아래를 ✅/❌로 보여주고 ❌가 있으면 고친 뒤 저장해: R-01이 오늘 데이터를 쓰는가 · R-02·R-03의 안내 문구가 칸마다 정확한 문장인가 · R마다 단위(UT)·통합(IT) 테스트가 하나씩 있는가 · 기대 결과가 구체적인가(숫자면 값까지) · 데이터 받기 실패 시 동작이 적혀 있는가
[지킬 것] 추측한 수치·출처·사례를 만들지 않는다 · API 키·비밀번호·개인정보를 묻거나 파일에 쓰지 않는다 · 투자 권유 문장을 쓰지 않는다 · 이 단계에서 말한 파일 밖은 수정하지 않는다 · PC에 프로그램을 설치하거나 프로젝트 폴더 밖에 파일을 만들지 않는다.
[끝나면] 파일을 저장한 턴에만 4줄로 보고해: ① 저장한 파일 ② 직접 열어 확인한 것 ③ 확인하지 못한 것 ④ 다음 단계 = M6-01 랜딩 먼저. 질문만 하는 턴에는 보고와 점검표를 붙이지 마.
[구현 전 UI 설계] 코드보다 먼저 docs/ui_design.md를 만들어. 공개 UI를 직접 보거나 내가 만든 관찰용 캡처를 references/ui_ref_01.png에 두고 Claude Code에 분석시킬 수 있어. 캡처는 로컬 관찰용이며 GitHub·Vercel·패들렛에 올리지 않고, 로고·스크린샷·글꼴·문구·이미지·화면을 복제하지 마. docs/ui_ref.md의 원칙만 가져와 내 데이터·내 문장·원본 CSS·SVG로 다시 설계해. 랜딩은 AIDA 순서로 ① Attention: 문제 한 줄+데이터 근거 ② Interest: 타깃 페르소나의 불편 순간·기존 대안 ③ Desire: 해결 방식·F-01 전후 흐름·가치 ④ Action: 실제 앱 미리보기+큰 CTA를 만들고, 마지막에 한계·출처를 작게 표시해. app.html은 R-01 정상·R-02 빈칸·R-03 오류 상태에서 무엇을 보여 줄지도 각각 그려. 화면 요소마다 연결된 요구사항 R-ID와 확인 방법을 적어.

[AI 최종 답변과 수강생 이동 게이트]
이 단계에서 AI가 낼 최종 답은 아래 네 줄뿐이야. 완료 기준 하나라도 증거가 없으면 「완료」라고 쓰지 말고 미확인으로 남겨.
① 저장: 실제로 저장한 파일과 전체 경로
② 증거: 완료 기준별로 「기준 | 파일·화면·수신함 등 증거 | 직접 확인됨/미확인」 표
③ 미확인: 아직 직접 확인하지 못한 값·화면·외부 결과와 이유
④ 다음: M6-01 — 수강생 확인이 끝난 뒤에만 진행
이번 단계의 통과 기준: R-01~R-03이 있는가 / R-01이 데이터를 쓰는가 / R마다 단위(UT)·통합(IT) 테스트와 기대 결과가 있는가
학생이 파일·화면·값을 직접 확인하고 「확인, 계속」이라고 말하기 전에는 다음 단계의 명령·파일 변경을 시작하지 마. R-ID별 확인 게이트가 있으면 그 표현(예: 「R-01 확인, 계속」)을 우선 적용해. AI의 설명·코드 생성·캡처만으로는 직접 확인됨으로 표시하지 마.

[실행·근거 이력]
이번 단계를 시작하기 전 docs/execution_log.md와 docs/evidence_log.md를 읽어. 없으면 제공된 양식으로 만든다.
작업을 실제로 수행한 뒤 execution_log.md에 한 줄을 추가해: 실행 시각 / 단계 ID / 한 일·사용한 명령 요약 / 입력 / 저장 결과 / 직접 확인한 화면·값 / 판정 / 미확인·다음 행동. AI가 추정한 내용은 「AI 제안」으로 표시하고 실제 실행과 섞지 마.
외부 숫자·기사·PDF·공개 데이터·수강생이 직접 확인한 화면을 사용했다면 evidence_log.md에 한 줄을 추가해: 근거 ID / 단계 ID / 주장·값 / 원천 URL 또는 파일 경로 / 발행·기준 시점 / 수집·확인 시각 / 라이선스·공개 가능 여부 / 한계 / 사용한 문서. 원문 전체·개인정보·계정·비공개 회사 자료는 저장하거나 공개하지 마.
이번 단계에서 새 외부 근거가 없으면 evidence_log.md에 「새 근거 없음」과 이유를 기록해. 로그 두 개는 다음 단계의 입력이며, 마지막 business_plan.md에는 evidence_log.md에서 직접 확인한 근거만 가져와.
