# 기능 하나부터 — 구현·오류 해결·로컬 테스트·배포

## 0. 어디서 시작하나요

1. 오늘은 **공개 데이터에서 찾은 내 서비스의 핵심 기능 1개 → 랜딩(index.html) + 앱(app.html) → Vercel 무료 주소**가 목표입니다. 주제가 없으면 `docs/data_cards.md`, 데이터는 `data/public/`을 봅니다.
2. Claude 앱의 Code 작업에서 내 프로젝트 폴더를 선택합니다. **모델은 반드시 Sonnet입니다.** Opus는 사용량 한도가 빨리 끝나 도중에 멈춥니다(모델 선택에서 Sonnet, 또는 대화창에 `/model sonnet`).
3. 오전: 데이터→주제 → 린캔버스 → 페르소나 → 저니맵 → GitHub 제출. 오후: 피드백 반영 → MVP·RICE로 F-01 → 요구사항·테스트 설계 → **랜딩 먼저 배포** → 앱 구현. 완성 예시는 `examples/fx_travel/`.
4. **오늘은 서버·API 키·로그인·결제를 만들지 않습니다.** 필요하면 `docs/guides/`의 Railway·GA4 가이드에 「다음 개선」으로 적어 둡니다.

## 1. 한 요구사항씩 구현하고 바로 테스트합니다

다음 명령을 Claude Code에 붙여넣습니다.

> docs/requirements.md와 docs/qa_scenarios.md를 읽어줘. 이번에는 F-01의 R-01만 구현하자. 먼저 연결된 테스트의 입력과 기대 결과, 수정할 파일을 보여줘. 적절한 단위 테스트를 만들고 구현 전 상태를 확인한 뒤 코드를 구현하고 실행해줘. 아직 연결이 없는 통합 테스트는 미실행으로 기록해줘. 구현 후 실제로 실행한 명령과 결과, 내가 브라우저에서 확인할 행동을 알려줘. 다른 기능을 추가하지 마.

브라우저에서 안내된 행동을 해봅니다. R-01이 되면 R-02, R-03을 같은 순서로 이어갑니다. 새 변경 뒤에는 관련 단위 테스트와 실행 가능한 통합 테스트를 다시 돌립니다. F-01의 정상·빈값·오류가 확인돼야 첫 기능 완료입니다.

> 이제 다음 미완료 요구사항 하나를 구현하고 해당 테스트를 실행해줘. 앞서 통과한 검사도 다시 돌려 기능이 깨지지 않았는지 확인해줘. 실행 결과는 test_log.md에 기록하되 실행하지 않은 검사를 통과로 쓰지 마.

## 2. 로컬에서 어떻게 열고 확인하나요 — 서버 없이

오늘 만드는 것은 HTML·JavaScript 정적 페이지라 **서버를 켤 필요가 없습니다.**

> 이 프로젝트는 서버 없이 index.html(랜딩)과 app.html(앱)을 더블클릭해서 열리게 만들어줘. 데이터는 fetch로 읽지 말고 data/public의 파일을 맨 위 data.js로 복사해 불러와줘. 외부 CDN·글꼴·라이브러리도 쓰지 마.

1. 탐색기에서 `index.html`(랜딩)과 `app.html`(앱)을 **더블클릭**해 브라우저로 엽니다.
2. 정상 입력, 빈 입력, 잘못된 입력을 순서대로 넣고 요구사항의 기대 화면과 비교합니다.
3. 파일을 고쳤으면 브라우저에서 **새로고침(F5)** 합니다. 안 바뀌면 다른 폴더의 파일을 열었는지 확인합니다.
4. 자동 검사는 `test.html`로 합니다. 「test.html을 더블클릭하면 R-01~R-03 검사가 돌고 맨 위에 n/3 PASS가 보이게 만들어줘. Node·Python·iframe·fetch는 쓰지 마.」
5. 요구사항에 저장 기능이 있으면 새로고침 뒤에도 결과가 남는지 봅니다.

## 3. 웹 화면에 오류가 뜨면

“안 돼요” 대신 **주소·누른 행동·기대한 결과·실제 결과·첫 오류**를 전달합니다.

|증상|먼저 볼 곳|확인할 것|
|파일을 열어도 빈 화면|탐색기에서 연 파일 위치|다른 폴더의 index.html을 열었는지·data.js 경로|
|빈 화면·버튼 무반응|브라우저 개발자 도구 Console|첫 오류 문장과 파일·줄 번호|
|자료/API만 실패|개발자 도구 Network|실패 요청의 상태 코드·응답. 인증 헤더/키 값은 복사하지 않음|
|배포 빌드 실패|Vercel 해당 Deployment의 Build Logs|실패한 명령과 최초 원인 오류|
|배포 후만 오류|브라우저와 Vercel Runtime Logs|실행 오류·경로·환경변수 이름/환경. 키 값은 출력하지 않음|

Windows Chrome에서는 F12 또는 Ctrl+Shift+J로 개발자 도구를 엽니다. 열리지 않으면 브라우저 메뉴의 개발자 도구를 사용합니다. Console에서 첫 오류를 찾고 Network에서 실패 요청을 확인합니다. 키·토큰·개인정보를 가린 뒤 전달합니다.

> R-__를 확인하다가 오류가 났어. 실행 주소: __. 재현 순서: __. 기대 결과: __. 실제 결과: __. Console/Network/터미널의 첫 오류: __. 재현해서 원인을 좁히고 필요한 부분만 수정해줘. 성공 기준을 바꾸거나 기능을 지워 통과시키지 마. 수정 뒤 해당 단위·통합 테스트와 기존 정상 경로를 다시 확인해줘.

## 4. 로컬 통과 후 GitHub에 올립니다

먼저 Claude에게 요청합니다.

> 현재 프로젝트의 배포 준비를 확인해줘. 핵심 기능의 단위·통합 테스트와 로컬 화면 확인 결과를 정리하고, 빌드 명령이 실제 있으면 실행해줘. 업로드할 파일과 제외할 파일을 구분해줘. .env·키·토큰·캐시·node_modules·수업 전용 시세·배포할 수 없는 PDF 원본을 제외하고, Vercel에서 실행할 프로젝트 루트·프레임워크·빌드/출력 설정을 파일 근거로 알려줘. 테스트하지 않은 항목은 별도로 적어줘.

초심자 소규모 프로젝트의 웹 업로드 경로:

1. GitHub에 로그인 → 새 저장소(New repository)를 만듭니다. 이름을 정하고 본인 저장소인지 확인합니다. 공개 범위를 확인합니다.
2. 저장소에서 파일 업로드(Upload files / Add file)를 엽니다. 위에서 확인한 배포 파일만 올립니다. 폴더 구조를 유지하고 불필요한 바깥 폴더가 한 겹 더 들어가지 않게 확인합니다.
3. 변경 설명을 적고 Commit changes로 저장합니다. **로컬 저장만으로 GitHub가 갱신되지는 않습니다.**
4. GitHub 파일 목록에서 시작 파일 또는 package.json이 의도한 위치에 있는지 확인합니다.
5. 파일 수·크기가 많거나 이미 Git을 연결한 프로젝트는 Claude Code에서 변경 목록을 확인하고 해당 프로젝트 파일만 commit/push하는 경로로 진행합니다. 둘을 중복으로 수행하지 않습니다.

## 5. GitHub 저장소를 Vercel에 연결합니다

1. Vercel 로그인 → 새 프로젝트(Add New → Project) → 방금 만든 GitHub 저장소를 선택해 Import합니다.
2. 저장소가 보이지 않으면 올바른 GitHub 계정과 해당 저장소 접근 권한을 확인합니다.
3. Claude가 파일을 보고 정리한 프로젝트 루트·프레임워크·빌드 명령·출력 폴더와 화면 설정을 대조합니다. 정적 HTML과 서버/API 프로젝트에 같은 설정을 강제하지 않습니다.
4. 서버 API가 있는 경우 필요한 환경변수를 해당 배포 환경에 추가합니다. 값은 지정 입력칸에 붙여넣고 화면 공유에 노출하지 않습니다. 브라우저에 포함되는 공개 변수에 비밀키를 넣지 않습니다.
5. Deploy를 누르고 결과를 기다립니다. 실패하면 Build Logs의 원인 오류를 확인해 앞의 오류 해결 절차로 돌아갑니다.
6. 완료 후 생성된 **https 배포 주소**를 엽니다. localhost 주소와 구분합니다.
7. 배포 주소에서 정상·빈값·오류·API 연결을 다시 확인합니다. 로컬 성공만으로 배포 성공을 판정하지 않습니다.
8. 수정했다면 로컬 테스트 → GitHub 반영 → 새 배포 완료 확인 → 배포 주소 재검사를 반복합니다.

GitHub와 Vercel은 역할이 다릅니다. GitHub는 코드를 저장하고 변경 이력을 관리하며, Vercel은 그 코드를 배포해 접속 주소를 제공합니다. 연결된 Git 저장소의 변경은 Vercel 배포를 유발할 수 있으므로 테스트한 변경만 올립니다. [Vercel Git 연결](https://vercel.com/docs/git) · [로그 확인](https://vercel.com/docs/logs)

## 6. Lv2~3 다음 기능으로

> F-01의 명세·단위/통합 테스트·로컬 확인 결과를 확인해줘. 미해결 핵심 결함이 없으면 MVP 후보 중 다음 기능을 골라 F-02로 추가하자. 필요한 요구사항과 테스트 설계부터 추가하고 한 요구사항씩 구현해줘. 매번 F-01 회귀 테스트도 실행해줘. 기능을 여러 개 동시에 추가하지 마.

Lv1은 F-01의 로컬·배포 동작 확인이 목표입니다. Lv2는 다음 기능·자기 데이터 연계를, Lv3는 기능 확장과 자동 테스트·반복 실행·실패 복구를 계속합니다. 새 기능 때문에 첫 기능이 깨지면 먼저 복구합니다.
